## CLOSED — `LeadClaim` production create-permission regression (2026-09-22)

**CONFIRMED, not intentional.** Production's `LeadClaim.create` RLS is `{}` (fully open, any caller) and `note` has no length cap. Both BACKUP and origin/main have `create: {user_condition: {role: admin}}` and `note.maxLength: 1000`. This is a genuine authorization defect on production, not a legitimate design divergence — established via first-party evidence, not inference:

- Commit `f0c282d` ("feat(leadClaim): move LeadClaim.create behind a validated server function (#40)", Aug 12 2026, authored by the repo owner) explicitly documents that production's live app *already had* `create` locked to admin-only at that time, and that this PR was bringing the GitHub repo up to match. The commit message also notes Dave reported the Base44 UI wasn't letting him approve the new `claimLead` function at that time.
- `base44/functions/claimLead/entry.ts`'s own code comment: "LeadClaim.create is restricted to admin in entity RLS ... this function is the elevated path, matching the pattern already used by moderate/entry.ts."
- The `claimLead` function (`base44/functions/claimLead/handler.ts`) is a fully validated, `asServiceRole`-elevated write path: validates `location_id` against a real Location record, bounds `operative_handle` (80 chars) and `note` (1000 chars), rejects a second active (pending/accepted) claim on the same location (409), and de-dupes in-flight requests per location. `asServiceRole` writes bypass entity RLS by design, so this function does not depend on `create` being open.
- **Confirmed the function is live on production right now**: `OPTIONS https://oohearth.app/api/apps/.../functions/claimLead` returns `204` (matching the handler's own OPTIONS-response code exactly).
- **Confirmed the deployed frontend already calls the function, not the entity**: fetched production's actual `ClaimLeadDialog-_RQzy5JA.js` chunk (found via live network requests on `/map`, not guessed) and found `X.functions.invoke("claimLead", {...})` — zero occurrences of direct `LeadClaim.create()`.
- A stale, unrelated hardcoded reference table in `src/pages/PortalOps.jsx` (`['LeadClaim', 'R/CREATE OPEN · U/D ADMIN']`) contradicts this — but it's a static display array with no functional connection to actual RLS enforcement, and git history shows it was never updated when `f0c282d` tightened the real permission. This is a documentation bug, not evidence of intended design.

**Conclusion**: production's currently-open `create` RLS provides zero additional value (the validated function is the only path the live UI uses) and is a pure liability — it lets any caller bypass all of `claimLead`'s validation (real-location check, duplicate-active-claim prevention, field length bounds) by hitting the entity API directly, and the missing `note.maxLength` removes even the schema-level backstop.

**Fix deployed 2026-09-22.** `LeadClaim.jsonc` — `create` → admin-only (byte-for-byte matching origin/main and BACKUP), `note` → `maxLength: 1000` + matching description (byte-for-byte matching origin/main and BACKUP). Zero application code changes needed or made. Human executed `npx --yes base44@0.1.14 entities push` from `prod-prerelease-patches/` (the same worktree Phase 2 used) after two rounds of mandatory preflight verification against a fresh authoritative production snapshot. Post-push, `GET /api/apps/6a62213cff3ccbca88c04ff5/entity-schemas` (cache-bypassed) confirms: exactly `LeadClaim` changed, matches the intended mirror 23/23, all other LeadClaim fields/RLS unchanged, 22 other entities unchanged, 0 new, 0 deleted, all 3 Phase 2 locks intact. DevTools smoke check (desktop + mobile: Home/Map/Globe/Location-Detail/Account) shows no regression. **CLOSED — SOURCE/SCHEMA VERIFIED. Not RUNTIME/behaviorally tested** (no actual LeadClaim creation attempted, per standing rule against synthetic production writes without separate authorization).

## OPEN — production `scanAd`/`migrateLocationImages` functions are behind origin/main, 2026-09-25 (SOURCE-VERIFIED, awaiting human authorization — NOT deployed)

**Discovered during a broader Base44/GitHub reconciliation pass** (function-by-function content pull + diff across production, BACKUP, and origin/main, using the CLI's own `functions pull` into isolated scratch directories — read-only, no writes). Both BACKUP and origin/main are hardened and match each other exactly; **production alone is missing both fixes below.**

### 1. `scanAd` — production is missing `validateMediaUrl()`'s host-allowlist check on `file_url`

- **PRODUCTION** (`main.ts`, pulled live): takes `file_url` straight from the request body with zero validation and passes it directly to `base44.asServiceRole.integrations.Core.InvokeLLM({ file_urls: [file_url], ... })`. Only gate before that call is `if (!caller) return 401` (any authenticated user, not admin-only — by design, since this is the normal field-report AI-scan path).
- **origin/main** (`base44/functions/scanAd/handler.ts`) and **BACKUP** (confirmed identical to main structurally and by grep for the same symbols): before calling `InvokeLLM`, validates `file_url` via `validateMediaUrl()` — must be `https:`, no embedded credentials, and either exactly `media.base44.com`, or `base44.app` with a path matching `/api/apps/{appId}/files/mp/public/{appId}/...` for *this app's own id*. Any other host is rejected before the LLM call ever fires.
- **IMPACT (reported precisely, not overstated):** any *authenticated* user (this app has open self-signup; "authenticated" is a low bar, not an admin gate) can currently make production's `scanAd` fetch/pass an arbitrary attacker-chosen URL into the vision-LLM call — at minimum an abuse vector (spend this app's paid AI-vision credits analyzing arbitrary internet images, unrelated to any real field report), and depending on how Base44's `InvokeLLM` integration resolves `file_urls` server-side, potentially an SSRF vector (fetching internal/private network addresses from Base44's own backend). **Not proven exploited — no test request was sent to verify the SSRF blast radius specifically; that would itself be a production security test requiring separate authorization.** This is reported as a confirmed source-level gap with a plausible-but-unverified worst case, not a proven incident.
- **origin/main also has real product-feature drift on top of the security gap**: main's `DETECTION_SCHEMA`/prompt recognize the 3 Public Space facility types (`skatepark`/`basketball_court`/`multi_use_court`) plus `facility_setting`/`facility_public_access`/`possible_relationship_type` fields for the already-shipped Public Space feature; production's schema stops at the original ad-surface types only. So production's AI scan currently gives zero facility-type assistance for Public Space submissions, even though the UI/schema/moderation support for those types is already live (see `00-CURRENT-STATE.md`'s "Public Space submission UI — ALREADY COMPLETE" entry) — a user can still manually pick a facility type, they just don't get AI help identifying one.
- **FIX:** deploy the exact already-tested `origin/main` source (`base44/functions/scanAd/entry.ts` + `handler.ts`, unchanged, already live on BACKUP) to production. No code needs to be written — this is a straight redeploy of existing, qualified code. Prepared command (**NOT RUN**): `npx --yes base44@0.1.14 functions deploy scanAd --app-id 6a62213cff3ccbca88c04ff5` from a fresh worktree at current `origin/main` (`0ed5688`), with the standard pre/post pull-and-diff verification.
- **AUTHORIZATION REQUIRED — Lane D (production function deploy).** Not deployed this pass. Flagging to Dave as the **highest-priority item found in this reconciliation pass** given it's a currently-live gap on the production app, not a theoretical one.

### 2. `migrateLocationImages` — production leaks `error.message` + `error.stack` to the HTTP response on failure

- **PRODUCTION** (`main.ts`, pulled live): the outer `catch` block returns `Response.json({ error: error.message, stack: error.stack }, { status: 500 })` — a raw internal error message and full stack trace go straight into the HTTP response body.
- **origin/main** (`handler.ts`) and **BACKUP** (confirmed matching): the outer catch instead does `console.error('migrateLocationImages error:', ...)` (server-side log only) and returns a generic `Response.json({ error: 'Migration failed' }, { status: 500 })` — no internals ever reach the client.
- **IMPACT:** this function's *normal* operation (listing/migrating broken image URLs) is admin-gated (`caller.role !== "admin"` → 403), so the main exposure window is narrow — but the leak is in the *generic* catch-all, which fires on ANY unhandled exception, including ones that could occur before or independent of the admin check completing (e.g., if `base44.auth.me()` itself throws for a malformed/expired token rather than returning falsy — not confirmed either way for this SDK version, main's code defensively wraps this exact call in its own try/catch specifically to not depend on that assumption, production's does not). Reported as a real, present information-disclosure pattern; not claimed as independently proven exploitable pre-auth.
- **FIX:** same as above — redeploy the existing, already-tested `origin/main` source. Prepared command (**NOT RUN**): `npx --yes base44@0.1.14 functions deploy migrateLocationImages --app-id 6a62213cff3ccbca88c04ff5`.
- **AUTHORIZATION REQUIRED — Lane D.** Not deployed this pass. Lower urgency than `scanAd` above (admin-gated, one-off maintenance utility, no evidence of external traffic reaching it), but same fix class and same "redeploy already-qualified code" shape — reasonable to bundle with the `scanAd` deploy if Dave authorizes both together.

**Both functions' actual authorization checks themselves (who's allowed to do what) are otherwise intact and correct on production** — this is specifically about a missing input-validation layer (`scanAd`) and a missing error-sanitization layer (`migrateLocationImages`), not a broken auth boundary. Also worth noting: `n8nPing`'s production `main.ts` carries a stale internal comment reading "PROPOSED PRODUCTION PATCH — not deployed" even though this is what's live right now (pulled directly from production) — a cosmetic/documentation inconsistency only, the actual hardened logic underneath matches the already-verified Phase 1 fix exactly; not a functional issue, not re-deploying just to fix a comment.
