## Globe markers incident — REOPENED, ROOT-CAUSED, FIXED, DEPLOYED, CLOSED (2026-09-23)

**Distinct from the P0 REST-fetch dedupe fix above — a completely different subsystem, completely different mechanism.** Dave reported directly: Home globe and Map's default globe view showed no markers on his own phone (Chrome/Android), while flat mode worked. The P0 dedupe fix (still deployed and effective — see above, unaffected by this) never touched this code path at all.

- **ROOT CAUSE (CONFIRMED via direct network + library-source tracing, not inferred):** `maplibre-gl` resolves its worker script by string-appending `maplibre-gl-worker.mjs` next to its own bundled chunk's runtime URL (`util/web_worker.ts:defaultWorkerUrl`) — a literal, unhashed filename Vite's content-hashed build output never produces. Live reproduction on production caught the exact request: `GET https://oohearth.app/assets/maplibre-gl-worker.mjs` → **404**. The GeoJSON source's worker actor never responds to any `setData()` call as a result — `isUpdatingWorker` stays `true` forever, `source.loaded()` never becomes `true`, **no console error is ever surfaced**. The "N spots" HUD text (`GlobeSection.jsx`) reads `markers.length` directly from the already-successful REST fetch — entirely independent of whether MapLibre ever finished processing that data into paintable tiles. This is why the bug was invisible to every prior check (including the original P0 investigation, which never touched Globe3D/MapLibre internals).
- **Confirmed general, not mobile-specific**: reproduced identically on desktop Chrome and 3 different mobile viewports (360/390-wide), same 404, same mechanism.
- **Confirmed as the correct and complete root cause**: a first fix attempt (`?url` raw-asset import of the worker file) resolved the outer 404 but left a *second*, identically-shaped silent failure — the worker's own internal `import ... from "./maplibre-gl-shared.mjs"` was preserved unrewritten by the raw copy, so that sibling chunk was never emitted and the worker still never became `loaded()`. Caught by direct instrumentation (walking the React fiber tree to the live `maplibregl.Map` instance and inspecting `getSource('ooh-markers').loaded()`/`_isUpdatingWorker` directly), not assumed fixed from the first attempt's build output alone.
- **FIX:** `src/lib/maplibreWorkerSetup.js` — `maplibregl.setWorkerUrl()` called with the worker imported via Vite's `?worker&url` suffix, which makes Vite treat the file as a genuine worker entry (parses and bundles its own import graph into one self-contained chunk) rather than a raw asset copy. Side-effect-imported from both `Globe3D.jsx` (Home + Map's globe view) and `MediaCorpGlobe.jsx` (the only other call site constructing its own independent `maplibregl.Map` with the identical vulnerable pattern — not reported by Dave, fixed proactively since it's the identical bug).
