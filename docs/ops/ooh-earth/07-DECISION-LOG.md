- **2026-09-22 — Strengthened the P0 fix from retry-only to retry + in-flight de-duplication, per explicit review request.** Retry-only addressed the observed symptom (a lost race occasionally recovers); de-duplication addresses the actual root mechanism (the 8-16x redundant concurrent request burst itself). Doing both was judged small and confidently testable, not a "large state-management rewrite" — implemented as two independently unit-tested ~20-line pure modules (`withRetry.js`, `dedupeInFlight.js`), not inline in the client.
- **2026-09-22 — Made `withRetry` selective (only retry plausibly-transient statuses) instead of retrying any error.** A blind retry-on-anything would hammer deterministic 4xx errors (400/403/404/422) that can never succeed on a second attempt. 401 is retried specifically because this incident diagnosed it as a session-readiness race, not a real auth failure — documented inline as an intentional, narrow exception to "don't retry 401" conventional wisdom.
- **2026-09-22 — Did not attempt synthetic fault injection (e.g., forcing a real 401) to "prove" the fix live**, since no request-mocking primitive was available in this session's toolset. This is a narrower claim than "we forced the exact failure and watched it recover," and is reported as such.
- **2026-09-22 — Reported production's request-count reduction precisely (8+ → 2) rather than claiming it matched BACKUP's (8+ → 1).** The difference is expected (production's larger dataset takes measurably longer per page fetch, widening the window for a second, non-overlapping `listAllLocations()` call to slip past the in-flight cache) and is still a large, real improvement — but overclaiming a cleaner number than what was actually observed would be dishonest.
