# Production observability runbook

This runbook covers the native, fail-open telemetry emitted by `submitOffline`,
`stripeWebhook`, `fieldStats`, and the admin-only `runtimeHealth` function.
It is designed for bounded Base44 log queries and avoids collecting user data.

## What telemetry means

Each event is one JSON log line with these stable fields:

- `timestamp`: ISO timestamp generated by the function runtime.
- `event`: currently `function.received` or `function.completed`.
- `function`: allowlisted function name.
- `correlation_id`: validated inbound `x-request-id`/`x-correlation-id`, or a server-generated UUID.
- `release`: `BASE44_RELEASE_ID`, `RELEASE_ID`, `GIT_SHA`, or `BASE44_FUNCTIONS_VERSION`; otherwise `unknown`.
- `outcome`: `success`, `rejected`, or `failed` on completion events.
- `duration_ms`: elapsed server time on completion events.
- `operation`, `entity`, `event_type`, `retryable`: bounded function-specific dimensions.
- `error_code`: one of the bounded codes below when applicable.

Error codes are `AUTH_REQUIRED`, `INVALID_METHOD`, `INVALID_INPUT`,
`DEPENDENCY_TIMEOUT`, `DEPENDENCY_FAILURE`, `SCHEMA_UNAVAILABLE`,
`REPLAY_CONFLICT`, and `INTERNAL_FAILURE`.

## Correlating a browser report

Capture the `x-correlation-id` response header from the failed request when the
client can access it. Pair that value with UTC time, route, and release. Never
ask a user to send request bodies, tokens, or screenshots containing personal
data merely to obtain a correlation ID.

## Bounded log inspection

Use the Base44 CLI with a function and a narrow time window. Query functions
individually; broad all-function requests have timed out in Production.

```sh
npx base44 logs --function submitOffline --since 1h --env prod -n 50 --json
npx base44 logs --function stripeWebhook --since 1h --env prod -n 50 --json
npx base44 logs --function fieldStats --since 1h --env prod -n 50 --json
```

Filter locally by `correlation_id`, `outcome`, or `error_code` without printing
the complete record into an incident channel. If no records are returned, say
“no records in the queried window”; do not infer that the function never ran.

## Investigating failures

1. Confirm environment and deployed release.
2. Query the affected function over a narrow UTC window.
3. Search for the correlation ID and completion outcome.
4. Use the error code to select the dependency or validation path.
5. Check the durable business ledger/entity before retrying a mutation.
6. Record the result and release revision in the incident log.

### Stripe webhook

`AUTH_REQUIRED` means signature verification failed. `DEPENDENCY_FAILURE` or a
retryable failed completion means the StripeEvent ledger did not reach a safe
completed state; allow Stripe to retry or follow the payment reconciliation
procedure. Do not replay arbitrary bodies or mark a ledger completed manually
without verifying the business identifiers. The telemetry contains event type
only—not signatures, customer data, metadata, or webhook bodies.

### submitOffline

`INVALID_INPUT` covers entity and operation-ID validation. A successful
completion with `operation: replay` means the server returned the existing
logical record. If a retry fails, preserve the client operation ID and inspect
the matching Location/FieldCheck record before retrying. Cross-instance
uniqueness remains runtime-dependent where Base44 has no unique constraint.

### fieldStats

`operation: cache_hit` indicates the in-process cache served the response;
`compute` indicates a fresh aggregate; `coalesced` indicates a concurrent call
shared the in-flight computation. A failure is sanitized to `Stats unavailable`.
Do not log or copy aggregate payloads into incident tickets.

### runtimeHealth

`runtimeHealth` is GET-only and admin-only. It returns status, a bounded release
identifier, timestamp, and a correlation header. It performs no entity scans or
writes. A 503 means the health check itself could not establish its safe result;
it does not prove that all user paths are down.

## Redaction rules

Never log or paste into telemetry: access tokens, authorization headers, Stripe
signatures or bodies, payment/customer details, email/name/address, wallet
addresses, uploaded URLs/content, user notes, prompts, model responses, API
keys, stack traces, or raw provider responses. The helper allowlists fields and
truncates bounded values; adding a new field requires a privacy review.

## Base44 limitations

Telemetry is native runtime logging, not a distributed trace system. Release
identity is `unknown` unless a deployment environment variable is configured.
Log retention, indexing, and query latency depend on Base44. The helper is
fail-open: logger/serialization failure never changes the business response.
Distributed uniqueness, transactions, and exactly-once processing are not
claimed by this runbook.

## Escalation and rollback

If telemetry volume or content is suspicious, disable the emitting call sites
in a normal Git change and redeploy; user flows do not depend on telemetry.
Preserve StripeEvent and operation records. Never delete logs or business
records as an observability “fix”.
